# omni 系统事实核查

## 目的

用当前仓库和安全的运行时证据回答“系统现在有什么”，避免把业务设想、历史记录或模型推断当成现状。只调查与需求有关的路径；不要为了写 PRD 扫完整个仓库。

## 证据台账

调查时维护一张台账：

| ID | 标签 | 结论 | 证据 | 核查方式 | 影响 |
|---|---|---|---|---|---|
| SYS-001 | `[现状事实]` | 一条原子事实 | `绝对路径:行号`、tool 返回或只读查询 | 代码已核/运行时已核 | 对设计的约束 |
| USR-001 | `[用户确认]` | 老板明确规则 | 用户原话摘要 | 会话 | 对范围的约束 |
| DES-001 | `[设计决策]` | PRD 推荐方案 | 对应章节 | 方案 | 为什么这样选 |
| ASM-001 | `[假设]` | 可逆默认项 | 暂无现状证据 | 待验证 | 验证和回退方式 |
| OPN-001 | `[待确认]` | 阻塞决策 | 冲突或缺口证据 | 待拍板 | 不决定会阻塞什么 |

一个单元格只放一个事实。代码存在只能证明“已实现”，不能自动证明“当前环境可运行”；需要时分别记录“代码已核”和“运行时已核”。

## 按事实类型选择权威来源

| 要核实的事实 | 首选来源 | 次选来源 |
|---|---|---|
| 业务路由、产品铁律、人工闸门 | 根 `AGENTS.md` 与对应业务 `SKILL.md` | `CLAUDE.md` |
| MCP tool 是否在正式清单 | `services/knowledge-engine/app/mcp/doctor.py` 的当前 `wanted` 集 | server 注册代码 |
| tool 参数、返回、错误和副作用 | `services/knowledge-engine/app/mcp/tools/` 实现与测试 | tool 文档 |
| REST/服务契约 | router + service 实现 + 测试 | OpenAPI/旧文档 |
| 数据表、字段、约束、状态 | migration、模型、当前 DB schema | 设计文档 |
| 页面、交互和反馈入口 | frontend 当前页面、组件、hook 与测试 | 截图/旧 PRD |
| LLM 行为 | `config/prompts/`、渲染代码、规则注入、模型配置与测试 | prompt 审计文档 |
| 当前能否运行 | doctor、测试、安全的只读 API/SQL | 代码存在性 |
| 历史原因和踩坑 | `docs/build-log.md` | 旧 plan/spec |

不同事实使用不同权威来源，不建立一个粗暴的全局优先级。来源冲突且影响 P0 时，把冲突写进 `OPN-*` 并暂停定案。

## 核查顺序

### 1. 锁定仓库和基线

- 用 `git rev-parse --show-toplevel` 找根目录。
- 读根 `AGENTS.md`；仅为跨客户端兼容时再核 `CLAUDE.md`。
- 记录日期、当前 commit；工作树有未提交改动时只写“dirty”，不要把别人的改动纳入本任务。
- 不读取 `.env`、cookie、token、口令或上传目录中的无关文件。

### 2. 从业务名词定位真实链路

先用 `rg` 搜用户用词、同义词、已有 tool/table/page/state 名：

```powershell
rg -n "关键词1|关键词2" AGENTS.md .agents services frontend migrations docs
rg --files services frontend migrations | rg "候选模块|候选页面|候选实体"
```

先看命中目录和文件名，再读最相关的小段。不要直接全文加载大 CSV、日志、构建产物或 `docs/build-log.md`。

### 3. 防止绕过已有业务 Skill

- 检查 `.agents/skills/`（版本化 canonical Skill 根）中是否已有该业务动作的唯一入口。
- 区分“现有业务 Skill 能完成的动作”和“为了支持新能力而需要改系统”。
- PRD 必须说明继续复用哪个入口；不能另造同义 tool、页面或状态机。

### 4. 追到执行与持久化

按实际数据流检查：

```text
用户/cron/外部事件
→ 页面、对话、IPC 或 API
→ router/MCP tool
→ service/provider
→ DB、文件或外部平台
→ 审计、反馈、指标和通知
```

对每一层核实：入口、输入、返回、错误、超时、重试、幂等、权限、审批、写入、状态变化和测试。缺一层就标缺口，不凭相邻层推断。

同一业务名词要反向核对“谁写、谁读、展示读哪张表”：搜索相近 table/store/API 名和所有引用，防止把平行真源误认为同一条链。若 writer 与页面 reader 落在不同实体，明确列为冲突或集成缺口，不能因名称相似而声称已打通。

### 5. 核查数据与状态

- 从 migration 和模型确认表名、字段、类型、null、唯一约束、外键、时区、单位和历史兼容。
- 现有数据是否足够属于运行时事实；只有确有必要时才做只读 SQL/API 查询。
- 新字段、表、索引、状态、版本或血缘一律标“拟新增”。
- 涉及回填、删除、状态改义或跨表迁移时，列出迁移前后、失败恢复和回滚可行性。

### 6. 核查 AI 与自动化

若需求涉及生成、RAG 或自动判断，核实：

- prompt 是否外置、模型从哪里选择、事实上下文如何注入。
- 是否返回 trace、是否接 prompt rules、是否有禁新增事实护栏。
- 召回为空、模型失败、部分失败时是 hard gate 还是 fail-open。
- 自动动作是否越过 Human Gate，是否有幂等、审计、成本和通知边界。
- 审批后延迟执行的副作用是否冻结被批准的 payload、目标、渠道和有效期，能否撤销，worker 是否只执行该授权快照并记录领取、防重和最终结果。

### 7. 做最小运行时验证

仅当动态状态会改变可行性时运行 doctor、目标测试或只读探针。先用现有测试和专用只读工具；不要为了 PRD 启动外部写操作、发布、采纳或真实抓取任务。

无法安全运行时写：`[现状事实·代码已核，运行时未核]`，并把验证命令放入实施前置项。

## 形成能力差距矩阵

每个目标能力只允许一个主分类：

- `复用`：现有能力满足，列证据和调用/依赖方式。
- `修改`：已有能力部分满足，列兼容扩展点。
- `拟新增`：证明当前没有，列最小落点与为什么不能复用。
- `不做`：退出 V1，列原因和再次纳入条件。
- `冲突`：与现有铁律或契约矛盾，列需要谁拍板。

最后检查有没有把“看见类似名称”误当成“行为完全满足”，以及有没有漏掉审计、反馈、指标、失败补偿和回滚这条尾巴。
