# 实施级 PRD 契约

## 1. 状态与文档信息

PRD 顶部必须包含：状态、版本、日期、需求方/决策人、系统基线 commit、关联需求原话。状态只允许：

- `DISCOVERY`：问题或结果尚未明确。
- `DRAFT`：已能评审，但有 P0 阻塞项或关键证据未核。
- `READY`：全部 Definition of Ready 项通过。

未知负责人、指标或日期写“待确认”，不得杜撰。`READY` 文档中不得残留影响 P0 的“待确认/TBD/TODO”。

## 2. 固定章节

模板中的 14 个二级章节必须保留；不适用时写“不适用 + 原因”。

1. **落地结论**：问题、推荐 V1、状态、复用/修改/拟新增摘要和首个阻塞项。
2. **背景、现场问题与目标**：用户、场景、现状流程、绕行方式、失败成本、目标和指标口径。
3. **当前系统事实**：证据台账和当前链路，不写未来方案。
4. **范围与非目标**：P0/P1、明确不做和再次纳入条件。
5. **目标流程与状态机**：入口、前置、主路径、人工确认、成功、失败、重试、退出。
6. **功能需求**：带 `FR-*` 的原子需求、优先级、规则、输出和异常。
7. **系统落点、复用与差距**：复用/修改/拟新增/不做/冲突及源码证据。
8. **数据、接口、工具与 AI 契约**：实体、字段、API/MCP、幂等、状态、血缘；涉及 AI 时写 grounding、prompt、trace、规则和 fallback。
9. **交互、权限、安全与审计**：入口和四态 UI、身份、敏感数据、副作用、Human Gate 与审计；能力链接需覆盖 token 范围、存储、过期、撤销、重放和泄漏面。
10. **异常、兼容、发布与回滚**：空数据、超时、部分失败、重复提交、migration、灰度和回退。
11. **可观测性与成功指标**：日志、指标、告警、反馈、业务口径、基线和观察窗口。
12. **验收标准**：`AC-*` 与 `FR-*` 可追溯的正常和失败用例。
13. **实施切片**：可独立验收的纵向切片、依赖、目标模块、测试和完成条件。
14. **风险、假设、待决策与 Definition of Ready**：分开列阻塞和非阻塞项，并逐项给 DoR 结果。

## 3. 功能需求写法

每项需求使用唯一 ID：

```text
FR-001 [P0] <短名称>
角色：谁
触发：何时
前置：系统必须处于什么状态
规则：确定性行为、边界和默认值
输出：用户可见结果和持久化/副作用
异常：空数据、无权限、超时、重复、部分失败
来源：USR/SYS/DES/ASM ID
```

一条 FR 只表达一个主要能力。P0 表示 V1 闭环必须；P1 表示可推迟且不破坏 P0。不要把技术任务伪装成功能需求。

## 4. 验收标准写法

统一格式：

```text
AC-FR001-01
Given：可复现的前置状态和数据
When：用户动作或系统事件
Then：外部可观察结果
And：数据、状态、审计或副作用
Evidence：UI/API/SQL/log/test 中如何验证
```

规则：

- 每条 AC 只验证一个主要行为，并明确关联一个已定义的 FR。
- 禁用“友好、快速、准确、稳定、智能”等不可测表述。
- 数字阈值必须来自用户决定、现有 SLO 或实测基线；没有依据就定义测量方法，不编目标。
- 每个 P0 至少覆盖正常路径；整个 V1 必须覆盖空数据、无权限、依赖超时/失败、重复提交和部分失败。确实不适用时在异常矩阵写理由。
- 数据 AC 写字段、格式、单位、时区和 null；状态 AC 写前后状态、版本和血缘；写操作 AC 验证授权、幂等与审计。
- LLM AC 验证 grounding、trace、不得新增事实和 fallback/hard gate；UI AC 验证 loading、empty、error、success 与反馈入口。

示例：

```text
AC-FR003-02
Given：生成节点无法获得要求的事实依据
When：用户提交生成请求
Then：系统返回约定的缺依据错误，不调用模型
And：审计记录失败状态与耗时，不创建 draft 产物
Evidence：tool 集成测试 + 审计表只读查询
```

## 5. 数据、API 与状态合同

仅在有证据或明确设计决策时写具体字段。对拟新增合同至少说明：

- 输入/输出 schema、必填/可空、单位、时区、大小限制和敏感等级。
- 成功、业务失败、系统失败和部分失败返回。
- 幂等键、唯一约束、并发冲突、重试和超时。
- 前后状态、非法跃迁、版本策略、父子关系和血缘。
- 写入与外部副作用的审批、审计、补偿和回放策略。
- 若使用审批/签名/能力链接，通知本身不能充当授权；写清 token 最小范围、单用途、hash-at-rest、短 TTL、服务端状态复核、撤销、防重放以及 URL/日志/Referer 泄漏防护。
- 对“现在审批、未来执行”的动作，写清不可变授权快照、目标/渠道、计划时间、有效期、撤销、worker 领取、防重以及执行结果审计。
- migration、历史数据、双写/兼容窗口和回滚限制。

现有名称附 `SYS-*` 证据；未来名称附 `[拟新增][DES-*]`。没有核实过的字段不要伪装成精确 schema。

## 6. 实施切片

优先拆成最小纵向闭环，例如：

1. 一个入口 + 一个契约 + 最小持久化 + 审计 + 正常/失败测试。
2. 完整交互四态 + Human Gate + 幂等/补偿。
3. 指标、反馈、灰度和自动化。

每个切片包含：交付结果、依赖、目标文件/模块、拟改或拟新增、测试、迁移/发布动作和 Done 条件。只有用户要求且有团队基线时才估工期；否则不编天数，可用依赖顺序表达。

## 7. Definition of Ready

以下全部通过才能标 `READY`：

- [ ] 使用者、现场问题、失败成本和目标结果明确。
- [ ] P0、非目标和成功指标口径明确。
- [ ] 当前系统能力有代码或运行时证据，冲突已处理。
- [ ] 每个 P0 FR 至少有一个可执行 AC，异常矩阵完整。
- [ ] 数据源、字段口径、单位、时区、null 和权限明确。
- [ ] API/tool 输入、输出、错误、超时、幂等、审批和审计明确。
- [ ] 状态机、版本、父子关系和血缘明确或证明不适用。
- [ ] 页面/对话入口及 loading、empty、error、success 明确。
- [ ] 涉及 AI 时，grounding、prompt、trace、规则、模型、事实护栏和 fallback 明确。
- [ ] 日志、指标、反馈、告警和执行后汇报明确。
- [ ] migration、历史兼容、灰度和回滚明确。
- [ ] 外部依赖、付费能力、凭证责任和 Human Gate 明确。
- [ ] 延迟副作用的授权快照、有效期、撤销、执行防重和结果审计明确或证明不适用。
- [ ] 测试环境、样例数据、验收方法和验收人可获得。
- [ ] 没有阻塞 P0 的 `OPN-*`、`TBD` 或未接受假设。
- [ ] 至少有一个可独立验收的纵向实施切片。
- [ ] `python -X utf8 scripts/validate_prd.py <prd-path> --strict` 通过。

validator 通过只代表结构、ID 与基础覆盖合格，不替代系统事实和业务决策复核。若任何关键项失败，将状态设为 `DRAFT`，分别列“阻塞开工”和“不阻塞开工”的事项。不要为了得到 `READY` 删除真实未知项。

## 8. 最终交接卡

在聊天中只交接：状态、一句话方案、关键复用/修改/拟新增、阻塞项、PRD 路径、validator 结果和恰好一个下一动作。PRD 交付不等于授权实施。
