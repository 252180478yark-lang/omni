# omni 降级与恢复 Runbook（L0-5）

> 蓝图 §4 L0-5【R 架构】· 阶段0。omni 的大脑就是家里这台 Win 主机上的一组 Docker 进程，
> 任何一环挂了都可能让"算账 / 出片 / 调研"停摆。本文档给每类故障一套
> **症状 → 检查 → 恢复 → 验证** 的固定动作，目标是**单点故障 30 分钟内恢复到"能重新算账/出片"**。
>
> 维护约定：本文档与 `docker-compose.yml`、CLAUDE.md「调试常用命令」段同生共死。
> 改了容器名/端口/启动顺序，必须同步改这里。

---

## 0. 可用性下限（恢复时间目标 / RTO）

| 维度 | 目标 |
|---|---|
| 单容器 crash（KE / hub / scout） | ≤ 10 分钟恢复 |
| 主机 / Docker 整机重启后冷启 | ≤ 30 分钟恢复到能算账/出片 |
| Postgres 数据损坏需回滚 | ≤ 30 分钟（从最近一次 `backup.ps1` 的 `pg_restore`） |
| 可接受数据损失窗口（RPO） | 上一次手动 `scripts\backup.ps1` 以来的变更（建议每日跑一次） |

> 这是**单人自用生产工具**的下限，不是 SLA。宁可慢一点恢复，也别引分布式/热备把系统搞复杂
> （参见全局记忆「omni 个人自用，禁止过度工程」）。远程接管/热备路径评估见 §6。

## 1. 服务拓扑速查（恢复时对照）

| 容器名 | 端口（host 127.0.0.1） | 角色 | 依赖 |
|---|---|---|---|
| `omni-postgres` | 5432 | 主数据库（业务 + 向量 + 审计 + 飞轮）| —（最底层）|
| `omni-redis` | 6379 | 缓存 / 队列 | — |
| `omni-ai-provider-hub` | 8001 | AI 网关（Gemini / Claude / 图像视频 provider）| — |
| `omni-knowledge-engine`（KE）| 8002 | MCP server + RAG + 业务 tool | postgres、redis、hub |
| `omni-scout-agent` | 8009 | 浏览器抓取（罗盘/云图/淘宝）| postgres |
| `omni-frontend` | 3000 | web /chat + 看板 | KE、hub |
| `omni-nginx` | 80（`0.0.0.0`）| 反代 + 三端入口 | 上面全部 |

启动依赖序：**postgres + redis（healthy）→ hub / KE / scout → frontend → nginx**。
（`docker-compose.yml` 已用 `depends_on: condition: service_healthy` 编排，`docker compose up` 会自动按序拉起。）

## 2. 主机 / Docker 重启后一键拉起

> 场景：Win 主机重启、Docker Desktop 重启、或手动全停后要恢复。

### 2.1 前置：确认 Docker daemon 活着
```powershell
docker info
```
- `Server:` 段为空 / `exit 255` → daemon 卡死。**托盘 Docker Desktop 图标 → Quit Docker Desktop → 重新启动**
  （只关 GUI 窗口不算，必须 Quit 整个 daemon；详见全局记忆「Docker Desktop daemon 诊断套路」）。等托盘图标变绿再继续。

### 2.2 一键拉起（按依赖序，compose 自动编排）
```powershell
cd E:\agent\omni
docker compose up -d
```
- compose 会先等 `omni-postgres` / `omni-redis` healthcheck 变 healthy，再起 KE/hub/scout，最后 frontend + nginx。
- 想看是否卡在某个 healthcheck：
```powershell
docker compose ps
```
  关注 `STATUS` 列：`healthy` = 好；`starting` = 还在初始化（postgres 首次最多等 ~100s）；`unhealthy` = 进 §3 对应章节。

### 2.3 验证（doctor 冒烟 + 关键 health 探针）
```powershell
# KE MCP tool 自检（应输出 63 项 tool 全 OK；数字对不上看 §3.3）
docker exec omni-knowledge-engine bash -c "cd /app && PYTHONPATH=/app python -m app.mcp.doctor"

# KE / hub / scout / notify 健康探针
curl http://localhost:8002/health
curl http://localhost:8001/api/v1/ai/providers
curl http://localhost:8002/api/v1/notify/health
```
- doctor 全 OK + 上述 curl 都有响应 → **恢复完成，可以算账/出片**。
- 任一不通 → 进 §3 对应故障章节。

## 3. 分故障 Runbook

### 3.1 Postgres 挂了（DB 不可用 / 数据损坏）

**症状**
- KE 报 `asyncpg` / `connection refused` / `could not connect`；算账(`query_costs`/`compute_margin`)、检索、审计全失败。
- `docker compose ps` 里 `omni-postgres` 不是 `healthy`。

**检查**
```powershell
docker compose ps postgres
docker logs --tail 100 omni-postgres
# 容器活着但连不上时，直连探活：
docker exec omni-postgres pg_isready -U omni_user -d omni_vibe_db
```

**恢复**
1. **只是没起 / 崩了一次**：
```powershell
docker compose up -d postgres
# 等 healthy 后，重启依赖它的服务（它们启动期连不上会卡）：
docker compose restart knowledge-engine scout-agent
```
2. **数据卷损坏 / 需回滚到最近备份**（损失自上次 `backup.ps1` 以来的数据）：
```powershell
# a) 找最近一次备份目录（backup.ps1 默认写到 E:\agent\omni\backups\omni-backup-<时间戳>\）
#    里面有 postgres-omni_vibe_db.dump（pg_dump -Fc 自定义格式）+ manifest.json
# b) 确保 postgres 容器在跑：
docker compose up -d postgres
# c) 把 dump 拷进容器并用 pg_restore 恢复（--clean 先清旧对象，注意会覆盖现有数据）：
docker cp "E:\agent\omni\backups\omni-backup-<时间戳>\postgres-omni_vibe_db.dump" omni-postgres:/tmp/restore.dump
docker exec omni-postgres pg_restore -U omni_user -d omni_vibe_db --clean --if-exists /tmp/restore.dump
docker exec omni-postgres rm -f /tmp/restore.dump
```
3. 兜底（备份缺失/无法回滚）：保留当前损坏卷别删，先让其他服务降级运行（见 §4），联系老板拍板是否接受重建空库。

**验证**
```powershell
docker exec omni-postgres pg_isready -U omni_user -d omni_vibe_db
# 关键表能查 = DB 恢复：
docker exec omni-postgres psql -U omni_user -d omni_vibe_db -c "SELECT count(*) FROM mvp_sku;"
docker exec omni-postgres psql -U omni_user -d omni_vibe_db -c "SELECT tool_name, status FROM mcp.tool_calls ORDER BY created_at DESC LIMIT 5;"
```

### 3.2 AI provider 限流 / 不可用（hub 报错或额度耗尽）

**症状**
- 生成类 tool（`generate_brief`/`generate_image`/`generate_video`/`competitor_*` 等）报 429 / 超时 / `anthropic-mock` 假响应。
- hub `/api/v1/ai/providers` 某 provider `available:false` 或 key 失效。

**检查**
```powershell
curl http://localhost:8001/api/v1/ai/providers
docker logs --tail 100 omni-ai-provider-hub
```
- 看哪个 provider 限流 / key 过期 / 模型名无效（坏模型名会**静默回退 mock**，见全局记忆「hub chat 用 gemini-3.5-flash」）。

**恢复**
1. **限流（429/额度）**：降频，等额度恢复；或临时切到另一个有额度的 provider/模型
   （改 `tool_models.yaml` 对应 tool 的 model）。**改完必须 restart KE**（`model_config.py` 有 `@lru_cache`，
   盘上 yaml 改了进程不知道，见全局记忆「tool_models.yaml 改完必须 restart KE」）：
```powershell
docker restart omni-knowledge-engine
```
2. **key 失效 / 轮换**：hub 启动期 `apply_persisted_provider_config` 会用 json override .env，
   **key 必须双改**：`services/ai-provider-hub/provider-config.json` + `services/ai-provider-hub/.env`
   （见全局记忆「hub provider key 必须双改」）。hub 是 build 模式，改完不能只 restart：
```powershell
# 改 key 后让 hub 生效（build 模式，restart 不够）：
docker compose up -d --build ai-provider-hub
```
3. **模型名无效导致假响应**：把 `tool_models.yaml` 里的坏模型名改成有效名（chat 用 `gemini-3.5-flash`），restart KE。

**验证**
```powershell
curl http://localhost:8001/api/v1/ai/providers   # 目标 provider available:true
# 跑一个便宜的生成 tool 看是否真响应（非 mock）。
```

> 降级取舍：provider 全限流时，**只读/算账链路（query_costs/compute_margin/检索）不受影响**，
> 优先保这条；生成类暂停，等额度。别为了出片硬刚平台风控（参见 §4）。

### 3.3 MCP 服务（KE）crash / tool 注册不全

**症状**
- Claude Code 调 omni tool 全失败 / MCP 连接断；`curl localhost:8002/health` 不通。
- doctor 报某些 tool 缺失，或总数 ≠ 63（CLAUDE.md「文档体检」基线）。

**检查**
```powershell
docker compose ps knowledge-engine
docker logs --tail 150 omni-knowledge-engine
curl http://localhost:8002/health
```

**恢复**
1. KE 是**源码 bind-mount 模式**（compose 挂了 `./app`/`./tests`/`./config`），改代码/prompt 后通常
   `docker restart` 即生效（prompt 文件靠 mtime 自检甚至不用 restart）：
```powershell
docker restart omni-knowledge-engine
```
2. 启动期就崩（import error / 语法错 / 依赖缺）：看 logs 顶部 traceback，定位是哪个 router/tool import 失败。
   本地可先 `python -m py_compile` 出问题文件确认语法。修好再 restart。
3. 依赖（postgres/redis/hub）没起导致 KE 卡启动：先按 §3.1 / §3.2 恢复依赖，再 restart KE。

**验证**
```powershell
docker exec omni-knowledge-engine bash -c "cd /app && PYTHONPATH=/app python -m app.mcp.doctor"
curl http://localhost:8002/health
```
- doctor 输出 tool 列表全 OK、总数 = 63 → KE 恢复。

### 3.4 Redis 宕（缓存层不可用）

**症状**
- KE / hub 报 redis `connection refused` / 认证失败；检索缓存 miss 变慢，部分缓存路径报错。
- Redis 多为**缓存**用途，宕了通常**降级可用**（直接回源 DB / 重算），不致命，但要尽快恢复。

**检查**
```powershell
docker compose ps redis
docker logs --tail 80 omni-redis
docker exec omni-redis redis-cli -a changeme_redis ping   # 期望 PONG（密码以 .env REDIS_PASSWORD 为准）
```

**恢复**
```powershell
docker compose up -d redis
# redis 恢复后，重启依赖它的服务清掉坏连接：
docker compose restart knowledge-engine ai-provider-hub
```
- 数据卷损坏（极少）：Redis 是缓存，可接受清空——停容器、删 `redis_data` 卷重建。**仅当确认里面没有不可重建的队列数据时才删**，拿不准先问老板。

**验证**
```powershell
docker exec omni-redis redis-cli -a changeme_redis ping   # PONG
curl http://localhost:8002/health
```

### 3.5 scout-agent 抓取链异常（cookie 失效 / 抓不到）

> 归类在降级里：抓数挂了**不影响算账/出片主链**，按"宁可数据旧也不冒封号"降级（蓝图 §7 / L0-6）。

**症状**
- `fetch_compass_*` / `fetch_yuntu_*` / `competitor_*` 返 `login_required` / `no_items` / 超时。

**检查**
```powershell
docker compose ps scout-agent
docker logs --tail 100 omni-scout-agent
```
- 看是 cookie 失效（登录态过期）还是 DOM 变更（选择器抓不到，落了 `snapshots/`）。

**恢复**
- **cookie 失效**：在能弹浏览器的 host 环境重登（罗盘/云图/淘宝各自的 relogin 流程，扫码/账密），
  cookie 落 `sessions/<平台>/user_data`（bind-mount 进容器）。**显式告警、不静默重试**（L0-6）。
- **DOM 变更**：scout-agent app 源码 bind-mount，调选择器后 `docker restart omni-scout-agent` 即生效，免 rebuild。
- **整容器没起**：`docker compose up -d scout-agent`。

**验证**：重跑一次对应抓取 tool / runbook，能拿到真实数据即恢复。抓不到先停手别狂刷（封号风险 > 数据旧）。

## 4. 部分降级运行（保主链、停旁支）

某些组件挂了**不必全停**，按"先保能算账/出片"的优先级降级：

| 挂了什么 | 主链（算账/出片）能否继续 | 降级动作 |
|---|---|---|
| scout-agent | ✅ 能 | 用已入库的旧数据，标"数据旧"；先修主链再说抓取 |
| redis | ✅ 能（变慢）| 回源 DB / 重算，尽快拉起 redis |
| AI provider 限流 | ⚠️ 只读/算账能，生成暂停 | 保 query_costs/compute_margin/检索；生成等额度或切模型 |
| frontend / nginx | ✅ 后端能（用 Claude Code CLI 直连 MCP）| web 看板暂不可用，CLI 链路照常 |
| postgres | ❌ 不能 | 最高优先级恢复（§3.1）；恢复前别做写操作 |

## 6. 远程接管 / 热备评估（L0-5 待老板拍板）

蓝图 L0-5 要求"评估 omni-orch 当远程接管/热备路径"。现状与结论：

- **omni-orch**（独立 repo `E:\agent\omni-orch`）是远程 Claude Code 编排 daemon，能在主机离线/出差时
  从手机经 PWA 触发 Claude Code 改代码、跑任务。它**可作"指挥链"的远程接管**（人在外面也能下指令），
  但**它不是数据热备**——omni 的 Postgres/向量库仍只在家里这一台主机上。
- **现实下限**：单点就是单点。真要异地热备需把 Postgres 同步到第二台机器，属"上层升级"而非现在要做的，
  **成本 > 单人自用的收益**，标 `needs_boss`。当前推荐的"接管"路径是：主机重启后按 §2 一键拉起（30 分钟内），
  出差期间用 omni-orch / Tailscale + SSH 远程拉起（见 `docs/multi-device/setup.md`）。

> 口径待老板拍板：是否要投入做"第二台机器 Postgres 流复制热备"。默认**不做**（保守、不过度工程），
> 维持"单点 + 快速恢复 + 远程指挥"三件套。— needs_boss
