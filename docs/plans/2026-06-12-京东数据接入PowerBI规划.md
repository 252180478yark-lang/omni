> 2026-06-12 v2（经两轮对抗评审修订）。摸底来源：scout-agent 代码实读 + live DB 实查 + 京东商家侧/Power BI 外部调研（5 路并行）+ 反过度工程评审 + 事实核查评审（实读 9 个文件验证）。
> 待老板拍板项见 §6；拍板后按 §3 切片施工。

## 0. 方案总览：快速通道 + 主线两段走

**快速通道（第 1 天就在 Power BI 看到京东数字）**：库里现成的京东静态数据（migration 044/045：渠道成本 204 行 + 物流运价 + 重量表）直接进 Power BI 出「三渠道利润测算」报表；老板登录商智手动导出 2-3 张核心报表 xlsx 扔进约定文件夹，Power BI Folder connector 接上出「京东销售日报」。**这一步同时完成了主线切片 0 一半的勘测产出**（免费版颗粒度够不够、数据长什么样、口径是什么）。

**主线（自动化爬取落库，老板点名要的）**：复用 scout-agent 抓数基建接入京东（先 POP 店：商智 + 京麦），数据统一落 `mvp_daily_metric`（`platform='jd'`，**先修 UNIQUE 闸门**），Power BI 经同一个 PG 入口读数，手动导出环节退役。

两段不互斥：快速通道半天-1 天，主线 5-8 天（诚实口径见 §7）。快速通道先跑还能在主线施工期间持续供数。

## 1. 现状摸底结论（已核实，带出处）

### 1.1 omni 侧
- **scout-agent 主轨** = catalog JSON 端点目录 + Playwright 登录态页面内 XHR 回放（`live_fetch.py` + `runner.js`，现 491 个已勘测端点，compass/doudian/yuntu 三平台）。新增平台挂点清晰（见 §3 切片 2）。
- **硬闸属实**：`mvp_daily_metric` UNIQUE(sku_id, date, metric_name) **不含 platform**（migrations/009 建表，034 只做了 expand STEP 1 加列回填；live DB `\d` 实查确认，当前 1396 行全 douyin）。`metric_ingest.py` 三处 upsert（:574/:602/:625）全是 `ON CONFLICT (sku_id,date,metric_name) DO UPDATE SET ... platform=EXCLUDED.platform`——京东若复用同名指标落同日，**静默覆写抖音行**，不报错。034 注释明文 STEP 2（UNIQUE 含 platform）等老板拍板。
- **写入点不止落库桥**（评审实查新发现）：`runbook_executor.py:398/:528` 和 `csv_parser.py:233` 也是同款 ON CONFLICT 且 INSERT 列里没有 platform——UNIQUE 改四列后这三处会直接报 `no unique constraint matching`，而 **runbook 套件每天 08:30 还在跑**，漏改 = 切片 1 上线次日早上 vision 轨落库就挂。
- **第二层坑**：UNIQUE 修好让双平台共存后，5 处读取点 WHERE 不带 platform 会把 jd 行混进抖音口径——scout `anomaly_engine.py`（4 处基线/序列查询）、`focus_pool_builder.py`（GMV TOP5）、`routers/dashboard.py`、`services/verification.py`、`routers/skus.py`。KE 分析半（business_analysis / query_metric_nl / query_metric_trend / 桌面 analytics REST）全部已带 platform 过滤（默认 douyin），安全。
- **`mvp_industry_benchmark` 整表无 platform 列**且 PK(date, category_id, metric_name)——京东同行标杆没地方落。
- **`mvp_sku` 是抖音形状**（douyin_product_id NOT NULL UNIQUE），京东商品落不进；migration 037 的 product/platform_listing 多平台脚手架在但 ingest 完全未用。
- **网络层零改造**：compose 已把 postgres 映射 `127.0.0.1:5432`（PG 16.13，库 omni_vibe_db）。全库只有 superuser omni_user 一个角色（repo 零 CREATE ROLE，live DB pg_roles 实查）——单人单机场景 Power BI 直接用它连即可，只读角色不是前置（见切片 3）。
- postgres 服务**无 restart 策略**，宿主机重启不自动拉起——顺手补一行，Power BI 才不会时不时连不上。
- **京东静态数据已在库**：`accounting.channel_product_costs`（jd_self 46 + jd_pop 41 行）、`channel_fees`（jd_pop 3.56%）、migration 044 物流运价/单瓶重量。⚠️ **jd_pop 侧 components 稀疏**（41 行里仅 18 行有快递费、费率类各 1 行；「毛保/推广费」是 jd_self 独有键）——利润报表 jd_pop 列会有空白，需核对源 xlsx 是否本来就缺，别误当数据丢失。

### 1.2 京东侧（外部调研，2026-06 现状，老板登录后台后二次核实）
- **京东商智**（sz.jd.com）：免费版含商品/交易/流量来源等基础分析，多页面有「导出表格」按钮；按天粒度下载、时段对比等进阶下载绑付费尊享版（商家版历史价约 8856 元/年）。数据约 10 分钟级刷新。
- **京麦/商家后台**：订单导出限流明确——同类型间隔 >10 分钟、每天 10 次；订单明细最长 31 天跨度、其余类型最长 60 天。
- **登录与风控**：扫码登录 cookie 约 1 天失效；手机短信验证码登录约 31 天（**消费侧 jd.com 经验值，商家后台实测为准**）；自动化登录会遇滑块验证码——通用做法是**人工登录拿登录态，自动化只复用登录态抓取**（与 omni 现有三平台模式一致）。
- **官方自研应用 API**（open.jd.com 宙斯）：免费、仅能访问本商家自有数据（合规利好），有订单/商品/库存接口；但要**企业实名（营业执照）+ HTTPS 且 ICP 备案的回调域名 + 接口审核 1-3 工作日**，且商智类经营指标（流量来源/转化漏斗）**无对应 API**。
- **自营（jd_self）**：数据在 VC 后台（vc.jd.com）品牌业绩/商品业绩/库存报表，可导出；**三套口径会打架**（品牌商智实时成交 / VC 业绩 / 结算单财务）——CLAUDE.md 已记录自营是供货制（毛保+推广费，非 GMV 扣点）。
- **技术未知数**：京东部分接口有 h5st 签名——scout 的 XHR 回放轨（runner.js 页面内裸放）能不能过，**必须切片 0 实测**；过不去就走「商智导出按钮自动化」轨。

### 1.3 Power BI 侧（外部调研，官方文档为主）
- Power BI Desktop **免费、无需登录**，Microsoft Store 安装；PostgreSQL connector 内置 Npgsql（**别手动装 Npgsql，会覆盖内置版**），Database 用户名/密码认证，本机无 SSL 只弹一次警告。
- **用 Import 模式，别选 DirectQuery**（本机小数据无意义，且将来个人网关不支持 DirectQuery）。
- **Desktop 本体没有定时刷新**——看数时打开 pbix 点 Refresh。要全自动得发布 Power BI Service：注册卡工作邮箱（老板 gmail 注册不了，要先开 M365 租户）+ 个人网关不能跑 Windows 服务，单人场景不值。
- 中文列名/中文值走原生 connector 基本无编码问题；乱码坑集中在 CSV 中转路线——**快速通道的 xlsx/CSV 若是自己导出脚本生成，必须 UTF-8 with BOM**（商智原生导出的 xlsx 无此问题）。
- 时区：`mvp_daily_metric` 落的是 date 列非 timestamptz，本机 Desktop 刷新无时区坑；只有将来上 Service 才需要在 SQL 层转 Asia/Shanghai（当前不做防御）。

## 2. 关键决策（带推荐）

### 决策 0：快速通道要不要先行
| 选项 | 内容 | 评 |
|---|---|---|
| **A. 快速通道先行（推荐）** | 第 1 天：静态维表报表 + 商智手动导出 xlsx → Folder connector。跑起来的同时主线照排 | 当天见数；手动导出本身就是切片 0 的勘测素材；主线施工期不断数 |
| B. 直接全做主线 | 不做手动导出环节 | 头 5-8 天 Power BI 里只有静态维表，动态数据要等管线通 |

**推荐 A**。日常动线：老板看完商智顺手点导出扔文件夹（约 2 分钟），主线通了这步退役。

### 决策 1：主线取数通路
| 选项 | 内容 | 优 | 劣 |
|---|---|---|---|
| **A. XHR 回放（推荐起步）** | 复用 scout catalog 主轨，勘测商智/京麦 XHR 建 catalog/jd.json | 与现有 491 端点同一套基建，落库桥/auth_health/scheduler 全复用 | h5st 签名风险未验证（切片 0 定生死） |
| **B. 导出按钮自动化（A 的兜底）** | Playwright 登录态点「导出表格」下载 xlsx → pandas 解析落库 | 不碰签名，商智官方功能，稳 | 颗粒度受免费版限制；导出限流要留余量；下载+解析层是新代码；taobao.py 反爬辅助全是模块私有，要新写 routers/jd.py 抄模式（两份代码会漂移） |
| C. 官方自研应用 API | 订单/商品/库存走宙斯 API | 最稳最合规，不怕风控 | 资质前置（企业实名+HTTPS 备案回调）；商智类指标无 API；二期再上 |

**推荐**：切片 0 勘测后在 A/B 里定主轨（很可能混合：能裸放的走 A，被签名挡的走 B）；C 列二期加固项，不挡第一期。

### 决策 2：落库方式
| 选项 | 内容 | 优 | 劣 |
|---|---|---|---|
| **A. 统一落 mvp_daily_metric（推荐）** | 先做 migration STEP 2（UNIQUE 含 platform）+ 配套整改 | 蓝图既定方向；跨平台对比同一张表；Power BI/桌面 BI/问数同源 | 要动核心表约束 + 6 个写入点 + 5 处读取层，一批做完 |
| B. 京东独立表绕闸门 | 新建 jd_daily_metric，Power BI 直读 | 零风险不碰抖音管线 | 永久双轨；跨平台对比泡汤 |
| C. 不落库，导出文件直接喂 Power BI | 即快速通道形态长期化 | 零 schema 改动 | 数据不进 omni（异动/问数/桌面 BI 永远看不到京东）；Folder connector 对 schema 漂移敏感 |

**推荐 A 为主线终态**（C 是快速通道的临时形态，不是终态）。配套口径：
- `mvp_industry_benchmark` 第一期**京东放弃同行对比**（表不动，少一个 needs_boss 级变更）。
- SKU 维度第一期**只落全店 `_SHOP_` 行**（京东商品维度对齐 platform_listing 留二期），先把店级日报跑通。
- metric_registry 注册京东指标时**中文名/alias 显式带「京东」限定**（如 `jd_gmv` / 「京东成交金额」）——京东 gmv 口径 ≠ 抖音 gmv_paid，同名不同义比缺数据更毒。代价：跨平台对比不能靠同名直拼，**在 bi 视图层做一次显式指标映射**（jd_gmv ↔ gmv_paid 对照表）来自圆。

### 决策 3：Power BI 刷新形态
| 选项 | 内容 | 适用 |
|---|---|---|
| **A. Desktop + 手动刷新（推荐）** | 落库全自动（scout 每天 09:00 ingest），看数时打开 pbix 点 Refresh（秒级）。已知风险：手动刷新的摩擦可能让报表渐渐没人看——出现这苗头就升级 B | 单人单机，零额外基建 |
| B. Windows 计划任务自动刷新 pbix | PowerShell 脚本定时刷 | 想要「打开就是新的」再加，半天活 |
| C. Service + M365 租户 + 个人网关 | 云端计划刷新 | gmail 注册不了 + 网关不能跑服务，**不推荐** |

## 5. 风险与已知坑（写给施工时的自己）
