# 块 1 · 多平台下钻指标 schema（SKU 身份解绑 douyin + platform 维 + roll-up 链）

> 对应 §0【R-29】§3【R-24/R-25】§6.1 + §8 阶段0/阶段1。
> 这是蓝图反复强调"最难改的地基"，也是分析面从 30% 走向可用的前提。

## 1.1 现状问题

1. **SKU 身份硬绑抖音**：`mvp_sku.douyin_product_id NOT NULL UNIQUE`（009 L9）。
   同一款酱油在淘宝/京东各有自己的商品 ID，当前模型**装不下第二个平台的同一个 SKU**——
   要么违反 NOT NULL，要么违反 UNIQUE。
2. **指标无 platform 维**：`mvp_daily_metric` 的 `UNIQUE(sku_id,date,metric_name)`
   （009 L45）把"一个 SKU 一天一个指标"锁死为单值。京东和抖音同一天同一指标只能存一个，
   互相覆盖 → 多平台对比连存都存不下。
3. **没有 roll-up 链**：要回答"总盘掉了 → 哪个平台 → 哪个品类 → 哪个活动/流量来源"
   （§6.1 下钻命脉），当前既无 platform 也无 channel/campaign/traffic_source 维度，
   下钻无从谈起。
4. **§0【R-29】诚实表述**：底座是"为抖音独养"的，京东淘天**零自有经营数据入库**——
   所以本块**先把 schema 形状改对（能装多平台），数据接入是 §8.5 独立子阶段**。

## 1.2 目标

把"SKU 身份"和"平台上架"解耦，让一个商品主体（SPU）可以同时在 N 个平台有 listing，
指标按平台分别落库，并建一条可下钻的 roll-up 链。**抖音存量 100% 不动、零回归**。

```
product (平台无关主体 / SPU)
  └── platform_listing (每平台一行：douyin / taobao / jd 的上架映射)
        └── mvp_daily_metric (+platform 列，按平台分别落指标)
              roll-up: 平台 → 品类(category) → SKU/SPU → 活动(campaign) → 流量来源(traffic_source)
```

> **关键决策：不动 `mvp_sku` 主键，新增旁挂表，而非掀桌重建。**
> 蓝图§3 说"数据攒到几十万条再改 schema 迁移成本几十倍"。但**直接改 mvp_sku 主键
> 会破坏所有现有外键**（mvp_daily_metric / pipeline.* 6 表 / cost_items 全挂
> sku_id → mvp_sku.id）。所以走**加法旁挂**：`mvp_sku.id` 继续当抖音 listing 的稳定锚，
> 上面盖一层 `product` 抽象，下游表零改动。这是"可加不可掀"在 schema 上的正确落地。

### 1.2.1 新表 A：`product`（平台无关商品主体 / SPU）

设计形状（**新建表，不动任何现有表**）：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | VARCHAR(64) PK | SPU 主键（如 `SPU-酱油-特级-500ml`，老板可读；或 uuid） |
| `name` | VARCHAR(200) | SPU 名（跨平台统一品名） |
| `category` | VARCHAR(100) | 品类（roll-up 用，归一） |
| `brand_id` | VARCHAR(64) | 品牌（对齐 5A/品牌心智的 brand_id） |
| `metadata` | JSONB DEFAULT '{}' | 规格/条码等扩展 |
| `actor_id` | VARCHAR(64) DEFAULT 'yark' | §R-26 预留（见块 3） |
| `created_at/updated_at` | TIMESTAMPTZ | |

> 起步阶段 `product` 可以和 `mvp_sku` **1:1 甚至留空**——抖音单平台时
> `platform_listing` 直接挂 `mvp_sku.id`，`product` 是"将来多平台时才填满"的占位抽象。
> 不强制现在就给每个抖音 SKU 建 product 行（避免净增老板录入负担，§1.8）。

### 1.2.2 新表 B：`platform_listing`（每平台上架映射）

这是解绑的核心表——把"商品在某平台的身份"从 mvp_sku 里抽出来：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | UUID PK | |
| `product_id` | VARCHAR(64) FK→product.id, **nullable** | SPU（可后补，不阻塞） |
| `platform` | VARCHAR(32) NOT NULL | `douyin` / `taobao` / `jd` … |
| `external_product_id` | VARCHAR(128) NOT NULL | 该平台的商品 ID（抖音=douyin_product_id，淘宝=item_id…） |
| `mvp_sku_id` | VARCHAR(64) FK→mvp_sku.id, **nullable** | 抖音存量回填指向现有行；非抖音平台为空 |
| `listing_url` | TEXT | |
| `status` | VARCHAR(32) DEFAULT 'active' | |
| `actor_id` | VARCHAR(64) DEFAULT 'yark' | §R-26 |
| `created_at/updated_at` | TIMESTAMPTZ | |
| | | **UNIQUE(platform, external_product_id)** —— 平台内商品唯一，跨平台不冲突 |

> **为什么 `mvp_sku_id` nullable**：抖音存量回填后指向现有 mvp_sku 行；淘宝/京东的
> 新 listing 没有对应 mvp_sku（mvp_sku 是抖音独有形状），留空，挂 product 即可。
> 这样**抖音继续走 mvp_sku 老路零改动，新平台走 product+listing 新路**，两套并存不打架。

### 1.2.3 `mvp_daily_metric` 加 platform 维（两步迁移，本块最敏感处）

**只加列，不改现有 UNIQUE 约束语义**——见 1.3 expand-contract。

| 新增列 | 类型 | 说明 |
|---|---|---|
| `platform` | VARCHAR(32) **nullable**（step 1）→ DEFAULT 'douyin' NOT NULL（step 2 收口后） | 该指标来自哪个平台 |
| `listing_id` | UUID FK→platform_listing.id, nullable | 可选精确锚（指标归属哪条 listing），缺省靠 sku_id+platform |

### 1.2.4 roll-up 下钻链（campaign / traffic_source 维）

§6.1 要求"平台→品类→SKU→活动→流量来源"。品类（category）已在 product/mvp_sku 有；
平台本块补；**活动 + 流量来源**两维，建议用**新增可空维度表 + 指标行可选外键**承载，
保持加法：

- `campaign`（活动维表，nullable）：`id / platform / name / starts_at / ends_at / actor_id`
- `traffic_source`：起步**不建表**，先在 `mvp_daily_metric.raw` JSONB 里带
  `traffic_source` 字段（抓数侧已有原始结构），等数据接入稳定后再决定是否升成正式维列。
  > 理由：§3【R-25】OLAP 例外——预聚合/维表升级是"可控存储层升级"，**不在阶段0 一次做满**，
  > 先留 JSONB 软维度，避免空表 + 过度工程（§1.7）。

### 1.2.5 预聚合表（§3【R-25】明确要求"设计阶段0就预留"）

为分析面下钻性能预留一张**物化/汇总表形状**（阶段0 只定义形状、可不立即物化）：

- `mvp_metric_rollup_daily`：`date / platform / category / metric_name / sku_count / value_sum / value_avg`
  PK `(date,platform,category,metric_name)`。由 cron 从 `mvp_daily_metric` 增量聚合。
  > 阶段0 **只建空表 + 写聚合 SQL 草案**，不接 cron（cron 是阶段1 看板的事）。
  > 目的：届时上 Metabase（§7【R-8】接现成 BI）直接读这张宽表，不在明细表上实时
  > group by 几十万行。

## 1.2.6 哪些指标归一、哪些保持抖音专属（口径地基，必须老板拍板）

§6.1 + §0【R-29】要求"多平台指标归一进库"，但**不是所有指标都能归一**。建议口径：

| 指标 | 归一？ | 理由 |
|---|---|---|
| **GMV（用户支付金额 gmv_paid）** | ✅ 归一 | 三平台都有"支付金额"概念，可比。**但口径需老板钉**（见 1.8 拍板点）|
| **毛利 margin** | ✅ 归一 | compute_margin 已支持 channel 维（channel_fees 已有 douyin/tmall/jd），口径统一后可比 |
| **ROI** | ✅ 归一 | §3 口径地基要求 ROI 由后端按唯一口径算（块 2/§6 关联）；三平台同公式才可比 |
| **流量结构（曝光/点击/转化漏斗）** | ✅ 归一（结构对齐） | 各平台漏斗阶段名不同，归一成统一漏斗阶段枚举（曝光→点击→成交）|
| **5A 资产（O/A1-A5）** | ❌ **保持抖音专属** | 巨量云图独有概念，淘宝京东无对应；硬归一 = 造假可比性 |
| **品牌心智（brand_mind）** | ❌ **保持抖音专属** | 同上，云图独有 |
| **完播率 / A3 转化等内容侧** | ❌ 抖音专属（内容面指标） | §6.1 归内容效果层，非跨平台商业健康层 |

> **设计落地方式**：归一指标走 `mvp_daily_metric(+platform)` 统一表，跨平台可
> roll-up；抖音专属指标**继续留在 `mvp_5a_*` / `mvp_brand_mind_daily` 原表**
> （009 已有，不动），分析面查询时**不 union 进跨平台聚合**，只在"抖音深度面"单独展示。
> 这样既满足"一套底座"（同库），又不制造伪可比（§1.7 反幻觉延伸）。

## 1.3 expand-contract 迁移步骤（§R-31 两步法）

> **三张新表（product/platform_listing/campaign/rollup）是纯新建，无 expand-contract 问题，一步建即可。**
> 真正需要两步的是 **`mvp_daily_metric` 加 platform 列**（动了几十万行的存量表）。

**Step 1 — expand（加 nullable 列，不加约束，不动 UNIQUE）**
1. `ALTER TABLE mvp_daily_metric ADD COLUMN IF NOT EXISTS platform VARCHAR(32);`（nullable）
2. `ADD COLUMN IF NOT EXISTS listing_id UUID;`（nullable，FK 暂不建或 NOT VALID）
3. 此时现有所有写入/查询**完全不受影响**（新列为 NULL，旧 UNIQUE 仍生效）。

**Step 1.5 — 回填（独立幂等脚本，见 1.4）**
4. 把存量行 `platform` 全部回填 `'douyin'`（现状 100% 是抖音数据）。

**Step 2 — contract（回填验证通过后，下一个 migration 才收口约束）**
5. 验证 `SELECT count(*) FROM mvp_daily_metric WHERE platform IS NULL = 0` 后：
   - `ALTER COLUMN platform SET DEFAULT 'douyin';`
   - `ALTER COLUMN platform SET NOT NULL;`
   - **替换 UNIQUE 约束**：旧 `UNIQUE(sku_id,date,metric_name)` →
     新 `UNIQUE(sku_id,date,metric_name,platform)`。
     > ⚠️ 这是本块**唯一一处"改"而非"加"**（替约束）。必须老板单独拍板。
     > 做法：先 `ADD CONSTRAINT ... UNIQUE(...,platform)`（新名），验证无冲突后
     > 再 `DROP CONSTRAINT` 旧的——expand-contract 内部再套一层，不留裸奔窗口。
6. FK `listing_id → platform_listing.id` 用 `ADD CONSTRAINT ... NOT VALID` 后
   `VALIDATE CONSTRAINT`（避免全表扫锁表）。

> **Step 1 与 Step 2 必须是两个独立 migration 文件、隔一段观察期**，禁同一文件一把梭。

## 1.4 回填 / 回滚

**回填脚本（独立、可重跑幂等）**：
```sql
-- 幂等：只填 NULL 行，重跑不覆盖已填的
UPDATE mvp_daily_metric SET platform='douyin' WHERE platform IS NULL;
-- platform_listing 回填：为每个现有 mvp_sku 建一条 douyin listing
INSERT INTO platform_listing (platform, external_product_id, mvp_sku_id, status)
SELECT 'douyin', douyin_product_id, id, 'active' FROM mvp_sku
ON CONFLICT (platform, external_product_id) DO NOTHING;  -- 幂等
```
> 回填脚本独立于 migration，可单独重跑；建议先 `--dry-run` 出影响行数给老板看。

**回滚（down）**：
- Step 1 可逆：`ALTER TABLE mvp_daily_metric DROP COLUMN platform, DROP COLUMN listing_id;`
  （回填的 'douyin' 随列一起没，无损——因为本来全是抖音）。
- Step 2 收口约束**标"半可逆"**：drop 回旧 UNIQUE 可恢复，但若届时已有非抖音行写入，
  回滚会因 `UNIQUE(sku_id,date,metric_name)` 撞键失败 → 必须先全量备份。
- 新表（product/listing/campaign/rollup）down = `DROP TABLE`，纯可逆。

## 1.5 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 替 UNIQUE 约束瞬间锁表影响生产 | 中 | 选低峰；ADD 新约束 → DROP 旧，不裸奔；几十万行量级锁窗很短 |
| 下游误以为 mvp_sku 要废弃 | 中 | 文档明写：抖音继续走 mvp_sku，product/listing 是"多平台才用"的旁挂，**不弃用 mvp_sku** |
| 空表幻觉（建好京东表没数据） | 低 | §8.5 显式标"等数据源"；本块只改形状不假装有数据 |
| 过度工程（一次把 traffic_source/预聚合做满） | 中 | traffic_source 先 JSONB 软维；rollup 先建空表不接 cron（§1.7）|

## 1.7 DoD（可机械判定，§R-11）

- [ ] `mvp_daily_metric` 有 `platform` 列且**存量行 100% = 'douyin'**（`count WHERE platform IS NULL = 0`）。
- [ ] 现有抖音读写**零回归**：现有 query_costs/compute_margin/scout 写指标路径不改一行代码仍跑通（抖音默认 platform）。
- [ ] 能插入"同 SKU 同日同指标的第二个平台值"而不撞 UNIQUE（新约束含 platform 后验证）。
- [ ] roll-up SQL 能从 `platform→category→sku` 三层聚合出数（哪怕只有抖音一个平台的数）。
- [ ] 5A/品牌心智表**未被并入**跨平台聚合（抖音专属隔离生效）。

## 1.8 需老板拍板的口径点（needs_boss）

1. **GMV 归一口径**：跨平台 `gmv_paid` **含不含退款/取消单**？三平台口径必须一致才可比。
   保守默认建议：**用"用户支付金额（gmv_paid）含未退款时点值"**，退款单独一指标，
   不直接从 GMV 扣（与现有 `gmv_paid` 命名记忆一致）。→ **待老板钉死。**
2. **ROI 定义**：ROI = GMV / 广告花费？还是 = 毛利 / 广告花费（更真实但需成本齐）？
   蓝图§5【R-4】要求 ROI 后端算、拒手填。**公式口径必须老板拍**（影响所有平台可比性）。
3. **product/SPU 是否现在就建满**：建议**不强制**（抖音单平台时 listing 直接挂 mvp_sku，
   product 留空），避免净增录入负担。→ 老板确认这个"懒填"策略。
4. **替换 `mvp_daily_metric` 的 UNIQUE 约束**：这是阶段0 唯一"改而非加"动作，
   单独拍板 + 改前 backup.ps1 验证恢复。

# 块 2 · tool_use_id 焊归因链

> 对应 §3 地基表"补 tool_use_id 焊归因链" + §5【R-4】+ §6.2【R-17】+ §8 阶段0
> DoD"差评→哪次调用→哪段 prompt 能精确 join"。

## 2.1 现状问题：为什么归因链"现在断"

实读 `audit.py` + `016` + `031` 后的物理根因，**链断在两个互不相识的 ID 空间**：

```
[Claude 端]  assistant message 里每个 tool 调用有个 tool_use_id（toolu_xxxxx）
                 │  这个 ID 进了客户端 stream-json，也被 message_feedback.tool_use_ids[] 存下来了
                 ▼
            ──── MCP stdio JSON-RPC (tools/call) ────  ← tool_use_id 在这层【丢失】
                 │  MCP 协议的 tools/call 请求体里【不含】Claude 的 tool_use_id
                 ▼
[KE 端]      audit.py wrapper 自己 gen_random_uuid() 造一个全新 tool_call_id
                 │  这个 uuid 跟 toolu_xxxxx 毫无关系
                 ▼
            mcp.tool_calls.id = 这个孤立 uuid
```

**断点精确定位**（三条独立证据）：
1. `audit.py` L64：`tool_call_id = str(uuid.uuid4())` —— KE 自己造 ID，**从不接收**
   Claude 的 tool_use_id。
2. `016 L6`：`mcp.tool_calls.id UUID DEFAULT gen_random_uuid()` —— 表里**没有任何列**
   能存 Claude 侧 tool_use_id。
3. `031 L23`：`mcp.message_feedback.tool_use_ids TEXT[]` —— 链的"另一半"
   （客户端→Claude 侧 ID）**已经存下来了**，只是 tool_calls 这头没有对应键可 join。

> **结论**：断的根因**不是"谁忘了写"，是 MCP stdio 协议层本身不透传 Claude tool_use_id**。
> spawn 出来的 claude CLI 子进程通过 stdio 跟 KE 的 MCP server 通信，
> `tools/call` 请求体里没有 `tool_use_id` 字段——KE 在协议层面**看不到**它。
> 所以这不是 KE 单方面加列就能修的，要在**能同时看到两个 ID 的那一层**搭桥。

## 2.2 目标

让"老板对某条消息打了差评（message_feedback）→ 精确定位到这条消息触发的
哪几次 tool 调用（tool_calls）→ 看那次调用用的哪段 prompt（trace）"能一句 SQL join 通。

## 2.3 设计：加法 migration + 三条可行传递方案（按可行性排序）

### 2.3.1 Schema 侧（纯加法，无争议，先做）

`mcp.tool_calls` 加两列（**只加，不动现有列**）：

| 新增列 | 类型 | 说明 |
|---|---|---|
| `tool_use_id` | TEXT, nullable | Claude 侧 `toolu_xxxxx`；拿不到时留 NULL（向后兼容）|
| `claude_session_id` | TEXT, nullable | 关联 `mcp.agent_sessions.claude_session_id`，session 维兜底 |

加索引：`CREATE INDEX ... ON mcp.tool_calls(tool_use_id) WHERE tool_use_id IS NOT NULL;`

> 这步是**无条件加法**，零风险、零回归（新列默认 NULL，现有写入路径不填也不报错）。
> 它把"接收侧的坑挖好"，至于坑里填什么由下面的传递方案决定。

### 2.3.2 传递方案（三选一，待老板拍板选哪条）

**方案 A（推荐 · 客户端侧 join，零侵入 MCP 协议）**
- 客户端（desktop/web runner）解析 stream-json 时，**已经能同时看到**：
  ① assistant message 里的 `tool_use_id`（toolu_xxx）+ tool_name + input；
  ② 这是哪个 session。
- 客户端把 `(claude_session_id, tool_use_id, tool_name, input_hash, ts)` 批量
  POST 给 KE 一个**新轻量 endpoint**（如 `POST /api/v1/mcp/tool-uses/link`）。
- KE 侧按 `tool_name + 时间窗 + args 近似` 把这批 tool_use_id **回填**到最近的
  `mcp.tool_calls` 行的 `tool_use_id` 列（类似 W1 切片的 `rate-recent` 按 tool_name
  取最近一条的思路，单人场景对齐可靠）。
- **优点**：完全不碰 MCP 协议、不碰 audit.py 核心；纯加一个 endpoint + 客户端一段
  解析。最符合"加法可逆"。
- **缺点**：对齐是"时间窗+tool_name 近似"非强一致；高并发会错配（但单人场景几乎无并发）。

**方案 B（强一致 · 但侵入度高）**
- 让 Claude 在调 MCP tool 时把 tool_use_id 作为一个**约定参数**透传进 args
  （如 system prompt 约定每次调用带 `_tool_use_id`）。
- audit.py 的 `_bind_args` 已经把所有 args 落 `mcp.tool_calls.args` JSONB——
  只要 args 里有这个键，**天然就存下来了**，甚至不用加列（但加列便于 join）。
- **优点**：强一致（ID 直接进 args）。
- **缺点**：依赖 prompt 纪律（Claude 可能漏传）；污染每个 tool 的入参语义；
  不如 A 干净。**不推荐当主路**，可作 A 的补强。

**方案 C（最稳但最重 · 不建议阶段0 做）**
- 从 Claude Code 的 `~/.claude/projects/<dir>/sessions/<uuid>.jsonl` 离线解析，
  把 tool_use_id ↔ tool_name ↔ ts 关系重建后批量回填。
- **优点**：数据最全（jsonl 是 ground truth）。
- **缺点**：离线、有延迟、要解析 Claude 内部文件格式（易随 CLI 升级变）。
  归档/补历史可用，不适合做实时主路。

> **建议**：阶段0 **先做 2.3.1 加列（无争议）+ 方案 A endpoint 骨架**；
> 方案 B 作为"args 里也带一份"的双保险（反正 args 已落库）；方案 C 留作补历史的工具。

## 2.4 回填 / 回滚

- **回填**：存量 tool_calls 的 `tool_use_id` 留 NULL（历史拿不到，不强补）。
  新数据从 endpoint 起逐步填上。方案 C 可选择性补一段历史。
- **回滚（down）**：`ALTER TABLE mcp.tool_calls DROP COLUMN tool_use_id, DROP COLUMN claude_session_id;`
  纯可逆，删列即回到现状（现有任何代码都不依赖这两列）。

## 2.5 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 方案 A 时间窗错配（并发） | 低 | 单人场景几乎无并发；错配率可监控，超阈值降级方案 C 补 |
| 依赖 Claude/MCP 协议未来变化 | 中 | 加列是协议无关的；传递层用方案 A（客户端侧）隔离协议风险 |
| 加列被误当"链已通" | 低 | 文档强调：加列只是"接收侧"，传递方案落地后链才真通；DoD 用真 join 验 |

## 2.6 DoD（§R-11 可机械判定）

- [ ] `mcp.tool_calls` 有 `tool_use_id` + `claude_session_id` 列（`\d mcp.tool_calls` 可见）。
- [ ] 对一条 `message_feedback`（rating='bad'），能用
  `message_feedback.tool_use_ids[] ∩ tool_calls.tool_use_id` **一句 SQL join** 出
  这条差评涉及的具体 tool 调用行 + 它的 args/result/trace。
- [ ] join 命中率可观测（新数据命中率应 > 阈值，如 80%；旧数据 NULL 不算）。

## 2.7 需老板拍板的口径点（needs_boss）

1. **选方案 A / B / A+B 双保险**？（推荐 A 主 + B args 双写补强）
2. 是否要方案 C 补一段历史 tool_use_id（成本=解析 jsonl，收益=补全旧差评归因）？
   保守默认：**不补历史**，只从今往后焊。

# 块 3 · actor_id 预留（R-26）

> 对应 §1.6【R-26】"所有反馈/留痕/决策表 schema 必须预留 `actor_id`（默认 = Yark），
> 使从单人长到小团队只需填字段而非改表结构"。

## 3.1 现状问题

蓝图§1.6 把"单人系统"明确为**易变业务假设**（团队一扩张就推翻），不是永久宪法。
当前**几乎所有反馈/留痕/决策表都没有 actor 维**——一旦第二个人（如运营助理）开始用，
无法区分"谁打的差评 / 谁报的 bug / 谁拍的板"，届时给几十万行存量表补 actor 字段
= 又一次几十倍成本迁移。**现在加 nullable 列（默认 yark）成本接近 0，将来不返工。**

> 个别表已零散有 actor 痕迹：`mvp_change_event.actor DEFAULT 'owner'`（009 L63）。
> 本块是把它**系统化、命名统一**为 `actor_id`（不动已有的 `actor` 列，避免改名破坏；
> 新表/新场景用统一 `actor_id`）。

## 3.2 目标

给"会随团队扩张需要区分人"的表统一预留 `actor_id VARCHAR(64) DEFAULT 'yark'`（nullable
或带默认），现在全是 yark，将来填真实 actor 即可，零结构变更。

## 3.3 哪些表加 actor_id（清单 + 理由）

按"这条数据将来需不需要区分是谁产生的"判断：

| 表 | 加 actor_id？ | 理由 |
|---|---|---|
| `mcp.message_feedback`（消息级反馈，031） | ✅ | 差评是谁打的 → 团队期诊断官要按人聚类 |
| `mcp.tool_calls`（工具留痕，016）的 `user_rating` 侧 | ✅（加 `rated_by` actor 列） | 谁评的这次调用；调用本身是 AI 发起不需 actor，但**评分**需要 |
| `mcp.bug_memory`（bug 库，032） | ✅ | 谁报的 bug / 谁标的已修 |
| `mcp.client_logs`（客户端日志，032） | ✅（可空，机器事件留空） | 人触发的操作留 actor，自动事件留空 |
| `mcp.decisions`（决策日志，017） | ✅ | "谁拍的板"是决策的一等属性 |
| `mcp.observations`（巡检登记，017） | ✅ | 谁创建/拥有这个巡检任务 |
| `pipeline.*` 6 表（matrix/audience/pack/script/asset，021） | ✅ | 谁跑的这版、谁采纳的（adopted_by 语义） |
| `pipeline.assets` 的投后 ad_metrics 回传 | ✅（`recorded_by`） | 谁回传的投后数据 |
| `product` / `platform_listing` / `campaign`（块 1 新表） | ✅（已在块 1 设计里带） | 谁建的商品主体/上架 |
| `accounting.cost_items`（成本，015/018） | ⚠️ **谨慎**，建议加但标 needs_boss | 成本涉及 real/public 可见性 + 钱，加 actor 要确认不影响 passphrase 逻辑 |
| `mvp_daily_metric` / `mvp_5a_*` / benchmark 等**抓数指标表** | ❌ 不加 | 机器抓的客观数据，无"人"概念；加 actor 是噪声 |

> **原则**：**人产生的主观/决策/反馈数据加 actor_id；机器抓的客观指标数据不加。**

## 3.4 设计形状（统一约定）

所有要加的表，统一加：
```sql
ALTER TABLE <t> ADD COLUMN IF NOT EXISTS actor_id VARCHAR(64) DEFAULT 'yark';
```
- **nullable + DEFAULT 'yark'**：现有写入路径不传也自动是 yark，**零回归**。
- 评分/采纳/回传类语义更精确的，用专名（`rated_by` / `adopted_by` / `recorded_by`），
  但都是同形状 `VARCHAR(64) DEFAULT 'yark'`，便于将来统一查"某人做了什么"。
- **暂不建 `actors` 维表**（单人期 over-engineering，§1.7）；actor_id 先是自由文本，
  团队期再升成 FK→actors 表（那时是加法，不返工）。

## 3.5 expand-contract / 回填 / 回滚

- **纯 expand，无 contract**：全程只加 nullable+default 列，**不加 NOT NULL 约束**
  （单人期没必要强约束；强约束反而限制将来匿名/系统行）。所以**不需要两步**，一步加列即可。
- **回填**：DEFAULT 'yark' 自动覆盖新行；存量行可选 `UPDATE ... SET actor_id='yark' WHERE actor_id IS NULL`（幂等）。
- **回滚（down）**：逐表 `DROP COLUMN actor_id`（或 rated_by/adopted_by/recorded_by），纯可逆。

## 3.6 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 一次性给太多表加列、migration 臃肿 | 低 | 可拆成"反馈表组 / 决策表组 / pipeline 表组"分多个 migration，独立可逆 |
| cost_items 加 actor 影响 real/public passphrase | 中 | 标 needs_boss，cost_items 单独评估，**默认本次不动 cost_items** |
| 误给抓数指标表加 actor 制造噪声 | 低 | 3.3 清单已明确机器表不加 |

## 3.7 DoD（§R-11）

- [ ] 3.3 清单里标 ✅ 的表（除 needs_boss 项）都有 `actor_id`/`rated_by`/`adopted_by` 列，默认 'yark'。
- [ ] 现有所有写入路径**零改动**仍跑通（新行自动填 yark）。
- [ ] 模拟"第二个 actor"：手动插一行 actor_id='helper' 能正常存，按 actor 聚合查询能区分。

## 3.8 需老板拍板的口径点（needs_boss）

1. **`accounting.cost_items` 加不加 actor_id**？涉及钱 + real/public 可见性，
   保守默认：**本次不动 cost_items**，留作单独评估。→ 老板确认。
2. 用统一 `actor_id` 还是按场景分 `rated_by/adopted_by/recorded_by`？
   建议：**统一 `actor_id` 为主**，仅 pipeline 采纳/投后回传用专名（语义更清），
   全部同形状。→ 老板确认命名口径。
3. 默认值用 `'yark'` 字符串可接受？（将来升 FK→actors 表时 'yark' 作为第一行 seed）。

# 附 · 三块的施工顺序建议 + 阶段0 整体退路（§8.5）

- **施工独立性**：块 2（tool_use_id 加列）和块 3（actor_id 加列）是**纯加法、零争议、
  可立即做**；块 1（多平台 schema）含唯一一处"改约束"，**最敏感、需最慎重 + backup 验证**。
- **建议顺序**：块 3 actor_id（最简单、暖身）→ 块 2 tool_use_id 加列（解锁归因 DoD）
  → 块 1 多平台（最难，单独拍板 + backup）。三块都可分别拍板、分别 apply。
- **§8.5 退路**：任一块做不完，**保留当前可用状态不半拉子上线**；块 1 的"京东淘天数据接入"
  本就是 §8.5 标"等数据源"的独立子阶段，schema 形状改好后空着等数据，不影响抖音日常运营。
- **本阶段对北极星（§0.5）的贡献**：块 1+块 2 直接服务"每个 SKU 有可追溯真实投后 ROI"
  （归因链通 + 平台维齐是 ROI 可算的前置）；块 3 服务"长到小团队不返工"（护持续可用）。
