# omni 后续开发功能总目录 —— 抖音全链路运营（2026-06-12）

> 怎么来的：六路并行盘点（规划文档 / 桌面蓝图审计 6 篇 / build-log 遗留项 / 在途分支 / DB 真实使用数据 / 能力暴露面）+ 一轮经营闭环完整性批判，全部条目有代码或 DB 实证，不是愿望清单。
> 用法：这是**一次定全的总目录**，之后按批次施工，不再想到一个做一个。每项标：现状（❌没有 / ⚡建了没通电 / 🔧半覆盖）、规模（S=半天~1天 / M=2~4天 / L=1~2周）、依赖。

## 〇、一页结论（先看这个）

**闭环形状：中段厚、两端薄、回路断。**
- 厚的（不用再建）：成本算账（470 次/月，全系统最高频）、内容生产 step2→3.6（3.5/3.6 刚上线即高频）、出片链工具齐全、桌面 BI 真在用（476 次）。
- 断的（最大杠杆）：**系统能大量生产"该投什么"，但完全回答不了"投了之后怎么样"**——投后回传 0 条真实 ROI、异动引擎 0 行产出、决策入档 0 真实行、315 个素材没有一个知道带没带货。
- 薄的：竞品只有一次性调研没有监控、直播/评价/达人/复购几乎空白、选品的市场侧输入没接。

**所以本目录的优先级哲学：先通电（让建了的转起来），再补强（内容生产短板），再扩面（数据监控覆盖），最后自动化。** 验收就盯三个数字：① `mvp_anomaly` 行数 > 0；② `pipeline.assets` 真实 ad_metrics > 0；③ 第一份"哪套内容真带货"榜能拉出来。
