# 路径 B · PRD：中台底座产品需求文档

> **核心定位**：在路径 A 验证使用习惯成立的基础上，建立**真正的电商运营中台**——多店多平台、SKU 全生命周期、跨模块数据飞轮。
>
> **路径 A 与路径 B 的关系**：路径 A 是 2 周的最小闭环验证，路径 B 是 4-6 周的中台底座。路径 A 的临时数据通过 SQL 迁移直接进入路径 B 的正式表，零浪费。

## 一、概述

### 1.1 业务愿景

把 omni-vibe 从一个"AI 工具集合"升级为一个**真正可以闭环运转的电商运营中台**。

老板（你）打开系统时不再是面对 13 个独立工具，而是看到一个围绕**「店铺 → SKU → 动作 → 数据」**统一组织的工作流，每个 AI 建议都有持久身份、每个动作都被追踪、每周都能看到决策的命中率。

### 1.2 中台必须解决的 4 个根本问题

| 问题 | 现状 | 路径 B 的解 |
|---|---|---|
| 模块按"能力"组织，不按"业务对象" | 13 项 sidebar 让人在能力间游走 | 7 项 sidebar 按使用场景组织；SKU 中心化 |
| AI 输出"用完即丢" | 无 decision_log | 强制全部落库 + 状态机完整流转 + 命中率追踪 |
| 模块间无数据流转 | 全靠手动复制 | "Send to..." 机制 + Focus Context 全局焦点 |
| 缺业务对象底座 | 无店铺、无 SPU、无统一 SKU | omni_core 三层底座（资产/数据/决策） |

### 1.3 与路径 A 的关系

路径 A 用临时表 `mvp_*` 跑通了 1 店 1 平台 5 SKU 的最小闭环；路径 B 在此基础上：

| 维度 | 路径 A | 路径 B |
|---|---|---|
| 店铺 | 1 个 | 多个（抖店 / 天猫 / 京东） |
| 平台 | 抖店 | 三平台都接 |
| SKU | 5 个占位 | 全店全 SKU + SPU 主数据 |
| 资产 | 字段化截图存证 | 完整 asset + asset_version |
| 决策日志 | 列表展示 | 中心化、筛选、状态机、命中率分析 |
| 跨模块流转 | 单向（chat/roundtable → log） | 双向 + 多目标"Send to..." |
| 数据库 | mvp_* 临时表 | omni_core / omni_data / omni_decision 三 schema |

### 1.4 项目目标（成功的衡量）

**3 个层面的成功标准**：

#### 层面一：使用层面
- 老板每天 5 分钟巡店 + 1-2 次单 SKU 深聊 + 必要时登记动作 + 周日 5 分钟复盘——成为习惯
- 7 项 sidebar 用起来比 13 项更顺手
- 任何 SKU 任何时刻能在 1 分钟内调出全景

#### 层面二：飞轮层面
- AI 建议命中率 ≥ 60%（连续 4 周）
- 每周采纳的建议中有具体的成功案例归档
- 跨平台对比能识别出"哪个平台 ROI 最高"

#### 层面三：扩展层面
- 接入新平台（如未来加拼多多）≤ 1 周工程量
- 加入新 SKU ≤ 5 分钟（自助流程）
- 加入新角色（如客服、运营助理）≤ 1 天

## 二、底层心智模型

### 2.1 「3 层底座 + 4 条使用流」总览

```
┌─────────────────────────────────────────────────────────────┐
│  4 条使用流（用户每天打开系统做的事）                          │
│                                                             │
│  ① 早晨 5 分钟巡店流（被动接收异动 + 决策待办）              │
│  ② 单 SKU 深聊诊断流（主动诊断 + AI 圆桌）                  │
│  ③ 动作执行登记流（极简登记 + 自动联动）                    │
│  ④ 周度决策复盘流（命中率分析 + 成功案例归档）              │
└────────────────────────┬────────────────────────────────────┘
                         ↕
┌─────────────────────────────────────────────────────────────┐
│  能力模块（被使用流调用，不直接是用户入口）                    │
│  内容工坊 │ 投放复盘 │ 知识对话 │ 圆桌诊断 │ 视频分析 │ 巡店  │
└────────────────────────┬────────────────────────────────────┘
                         ↕
┌─────────────────────────────────────────────────────────────┐
│  3 层底座（所有模块共享的核心数据）                           │
│                                                             │
│  ① 资产层：店铺 → SPU → platform_instance → asset → version │
│  ② 数据层：daily_metric + anomaly + scout_run               │
│  ③ 决策层：change_event + decision_log + verification       │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 SPU + platform_instance 双层抽象

**业务现实**：同一款"零添加生抽 500ml"在抖店、天猫、京东各开一个链接，链接数据独立、人群不同、详情页不同。

**数据模型**：

```
SPU（你脑子里的"那一款生抽"）
└── spu_id: S001  名称: 零添加生抽 500ml  类目: 调味品/酱油
    ├── platform_instance（抖店）：shop=153xxxx, sku=153xxx-456
    ├── platform_instance（天猫）：shop=88xxx, sku=item-789
    └── platform_instance（京东）：shop=44xxx, sku=jd-321

资产 / 动作 / 数据 / 决策
全部挂在「platform_instance」上，少数共享资产标记 shared_with=[douyin, tmall]
```

### 2.3 决策日志中心化

**所有 AI 输出强制落库**，不允许"用完即丢"：

| 来源 | 写入时机 | 状态机 |
|---|---|---|
| 圆桌讨论 | 会议结束 → 自动写 | pending → adopted/rejected/postponed |
| 异动检测 | 检测到异动 → 自动写 + 自动诊断 | 同上 |
| 投放复盘 | 复盘报告生成 → 自动写 | 同上 |
| 知识库问答 | 用户点"存入" → 写 | 同上 |
| 内容工坊 | brief 生成 → 自动写 | 同上 |
| 手动 SKU 诊断 | 触发深度诊断 → 写 | 同上 |

**采纳路径**：决策被采纳 → 自动建一条 `change_event`（待执行）→ 用户去店铺执行 → 数据回流 → 7 天后 verification 自动跑 → 决策状态变 verified → 命中率统计更新。

### 2.4 跨模块流转机制

每个 AI 输出右上角都有 "→ Send to..." 菜单：

```
┌─ AI 圆桌讨论结果 ────────────┐
│ ...                          │
│                          [→] │ 
│                              │
│ ─ Send to ─────────────────  │
│ → 关联到 SKU                 │
│ → 用作内容 brief             │
│ → 创建投放复盘               │
│ → 派发为动作项               │
│ → 存入决策日志（默认强制）    │
└──────────────────────────────┘
```

### 2.5 工作焦点（Focus Context）

全局保存"你当前在跟踪的 SKU/问题"：

- 选中 SKU 后，所有模块的输入都自动预填这个 SKU 的上下文
- 打开 chat 时，系统提示"我的当前焦点是 [SKU]，关于它最近的状态是…"
- content-studio 创建 brief 时默认挂载这个 SKU
- 知识库问答时自动注入 SKU 的多平台数据 + 资产快照
- Esc 键或显式退出焦点

## 三、范围

### 3.1 在范围（必交付）

#### 3.1.1 多平台支持

| 平台 | 第几周 | 接入方式 |
|---|---|---|
| 抖店 | 已就绪（路径 A） | 升级现有 runbook 接 platform_instance |
| 天猫 | Week 3-4 | 新建 generic_harvester（生意参谋） |
| 京东 | Week 5-6 | 新建 generic_harvester（商智） |

#### 3.1.2 全 SKU 支持

- 任意数量 SKU（设计上限 1000+）
- SPU 主数据导入（CSV 批量 + 单条添加）
- 平台 SKU 自动映射（基于商品标题模糊匹配 + 人工确认）

#### 3.1.3 完整 SKU 详情页（7 Tab）

| Tab | 内容 |
|---|---|
| 概览 | 多平台关键指标对比 + 主推等级 + 最近动作 + AI 建议待办 |
| 资产 | 资产版本树（主图/详情页/标题/价格/视频/人群包），按平台分组 |
| 数据 | 多维度趋势图，可叠加动作变更线，跨平台对比 |
| 动作 | 完整动作日志 + 前后对比卡 |
| AI 诊断 | 决策日志（按 SKU 筛）+ 启动深度诊断 |
| 内容 | content-studio 关联此 SKU 的所有物料 |
| 客服 | 评价摘要 + 客服会话痛点 + 售后问题归类 |

#### 3.1.4 决策日志中心完整版

- 路径：`/decisions`
- 功能：列表 / 筛选（状态/类型/SKU/平台/时间）/ 搜索 / 批量操作 / 状态机完整流转
- Dashboard：本周命中率 / 来源分布 / 平均处理时长 / 顶部成功案例 / 顶部失败教训

#### 3.1.5 周度 Dashboard

- 路径：`/dashboard/weekly`
- 多张可视化图表：
  - 总 GMV/UV/CVR 7 日 / 28 日趋势
  - 各 SKU 热力图（涨跌幅）
  - 各平台 ROI 对比
  - 动作 - 数据时间轴叠加
  - AI 命中率分布
  - 客服痛点 word cloud

#### 3.1.6 客服数据接入

- 抖店客服会话抓取
- 天猫千牛会话抓取
- 京东京麦会话抓取
- LLM 痛点分类 + 趋势分析
- 高频问题 → 自动建议详情页/标题优化

#### 3.1.7 跨模块流转

- 所有 AI 输出右上角 "Send to..." 菜单
- Focus Context 全局焦点
- content-studio brief 接入 SKU 数据
- ad-review campaign 关联 SKU
- 圆桌讨论可"以 SKU 为对象"

#### 3.1.8 Sidebar 精简

从路径 A 的 5 段 17 项 → 路径 B 的 7 项 + 系统二级：

```
🏠 工作台
📦 我的店与产品
🎬 内容工坊
🎯 投放与复盘
🧠 知识与对话
📊 数据与归因
─────
⚙ 系统（二级菜单：模型/任务/Prompt/控制台）
```

### 3.2 不在范围

| 类别 | 说明 |
|---|---|
| 多人/团队协作 | 单用户为主，预留权限模型，下一阶段实现 |
| 移动端 | Web 桌面端为主 |
| ERP 集成（库存/财务） | 留给后续阶段 |
| 直播带货实时数据流 | 现有 livestream-analysis 维持事后分析 |
| 第四个平台（拼多多/快手） | 留给后续，但接入接口设计要预留 |
| 算法级归因（双重差分/合成对照） | 路径 B 仅提供前后窗口对比，进阶归因留给后续 |

## 四、用户与场景

### 4.1 用户画像

同路径 A，但加：
- 单用户深度使用 4-6 周后，对系统有了自己的"使用偏好"
- 期望系统能学到这些偏好

### 4.2 关键使用场景（4 条使用流）

#### 流 1：早晨 5 分钟巡店流

```
8:30 ─── scout-agent 跑完所有平台 runbook
8:35 ─── 异动检测 + 跨平台聚合分析
8:40 ─── 企微推送（含跨平台维度："SKU-A001 抖店跌天猫涨"）
9:00 ─── 你打开 /workspace
9:00-9:05 处理 3-5 张异动卡片
        红色卡片 → 跳 SKU 详情 → 看跨平台对比 → 启动诊断或采纳建议
        黄色卡片 → 处理待办决策
        绿色卡片 → 享受成就感 → 决定是否复用打法
9:05 ─── 关电脑
```

#### 流 2：单 SKU 深聊诊断流（升级版）

```
你：在 /workspace 点 🔴 SKU-A001 异动卡
   → 跳到 /sku/SKU-A001 详情页
   → 默认显示「全景」视图（三平台对比）
你：发现"抖店 GMV 跌而天猫涨" → 切到「抖店」Tab
   → 看 14 天数据 + 最近动作 → 找到拐点
你：切到「AI 诊断」Tab → 点「启动深度诊断」
系统：
  - 拉本 SKU 14 天三平台数据
  - 拉本 SKU 资产版本树
  - 拉知识库相关人群报告（"调味品/酱油"类目）
  - 拉客服评价摘要
  - 调用圆桌讨论（运营/数据/内容/客服 4 视角）
  - 圆桌结束 → 自动落 decision_log
你：阅读建议 → 「采纳」"抖店换主图突出零添加场景"
系统：自动建 change_event（待执行，关联抖店 instance）
你：去抖店后台执行 → 回来登记动作（自动联动 ）
```

#### 流 3：动作执行登记流（升级版）

**两条路径合并**：

##### 路径 A1：从决策采纳（自动联动）

```
你点决策日志「采纳」按钮
→ 系统自动建 change_event，预填：
  - SKU
  - 平台（决策中说明的）
  - asset_type（决策推断）
  - 优化意图（决策中提取）
  - 描述（取决策标题）
你只需要：
  - 执行后回来确认（标 executed=true）
  - 上传截图（可选）
```

##### 路径 A2：手动登记（路径 A 已有）

```
SKU 详情页 → 「+ 登记动作」 → 填表 → 提交
```

#### 流 4：周度决策复盘流（升级版）

```
周日 21:00
你：进 /dashboard/weekly
看到：
  - 本周决策状态：已执行 12 / 已验证 8 / 待执行 4
  - AI 命中率：65%（5 正向 / 0 负向 / 3 中性 / 4 待审）
  - 跨平台对比：抖店 vs 天猫 vs 京东 ROI
  - 顶部成功案例：3 条（自动归档为可复用策略）
  - 顶部失败教训：2 条
  - 客服痛点 word cloud
  - 动作类型分布（哪类手段做得最多/有效）
你：处理 4 条 pending 决策
你：查看异动趋势：本周 12 条异动，9 条已处理，3 条仍未结案
你：30 分钟内完成本周复盘
```

- [ ] ≥ 6 张图表：GMV 趋势 / SKU 热力图 / 平台 ROI 对比 / 动作 - 数据时间轴叠加 / AI 命中率分布 / 客服痛点 word cloud

- [ ] 自动归档"本周成功案例"和"本周教训"
- [ ] 支持导出 PDF 周报

**优先级**：P0

### 故事 B08：客服数据接入与痛点分析

## 六、功能需求（高层）

详细设计见「02-施工」。这里给业务可读概览：

### 6.1 资产层（omni_core）

```
shop                        多店铺管理（platform: douyin/tmall/jd）
sku                         SPU 主数据
sku_platform_link           SPU × 店铺 → 平台 SKU 映射
asset                       资产定义
asset_version               资产版本（含截图/文件 + 上线时间）
audience_pack               人群包（按平台不同：抖店云图/天猫达摩盘/京东 DMP）
```

### 6.2 数据层（omni_data）

```
daily_metric                每日指标（必带 platform_instance_id）
anomaly                     异动事件
scout_run                   巡店执行记录
platform_session            各平台登录态
customer_session            客服会话（脱敏后）
review                      平台评价
pain_point                  痛点分类（LLM 提取）
```

### 6.3 决策层（omni_decision）

```
change_event                动作日志
decision_log                AI 决策日志（含状态机）
verification                前后对比验证结果
success_case                归档的成功案例
failure_lesson              归档的失败教训
focus_context_history       工作焦点历史（用于"返回上次焦点"）
```

### 6.4 Sidebar 重构

```
🏠 工作台 (/workspace)            首页：推送 + 待办 + 巡店状态
📦 店与产品 (/shops, /products)   多店树状视图 + SKU 列表
🎬 内容工坊 (/content)            content-studio + video + briefs（合并）
🎯 投放与复盘 (/marketing)        ad-review + flywheel + audience-pack
🧠 知识与对话 (/intel)            knowledge + chat + roundtable + qa
📊 数据与归因 (/insights)         dashboard + decisions + verifications
─────
⚙  系统 (二级菜单)                models / tasks / prompt-lab / 控制台
```

**重定向**（保留旧 URL 不破坏书签）：
- `/chat` → `/intel/chat`
- `/knowledge` → `/intel/knowledge`
- `/ad-review` → `/marketing/review`
- ...等等

### 6.5 SKU 详情页 7 Tab

详细见 02-施工 §5。这里列概念：

| Tab | 数据来源 |
|---|---|
| 概览 | 三平台聚合 daily_metric + recent change_event + pending decision_log |
| 资产 | asset + asset_version（按 sku_platform_link 分组） |
| 数据 | daily_metric 全维度 + 时间轴叠加 |
| 动作 | change_event + verification |
| AI 诊断 | decision_log（filter sku_id） |
| 内容 | brief + material（filter sku_id） |
| 客服 | review + customer_session + pain_point |

### 6.6 工作焦点（Focus Context）

```
全局 Zustand store：focusStore
  current_sku_id?: string
  current_shop_id?: string
  current_platform?: 'douyin' | 'tmall' | 'jd'
  set / clear

UI：所有页面顶部有 FocusBar 组件，显示当前焦点 + 一键清除
注入：chat / roundtable / content-studio / ad-review 都从 focusStore 读取
持久化：localStorage（路径 A 已有 zustand persist）
```

### 6.7 决策中心 + Dashboard

```
/decisions                  决策日志中心（完整功能）
/dashboard/weekly           周度复盘
/dashboard/anomalies        异动总览
/dashboard/verifications    验证总览
```

## 十、依赖与风险

### 10.1 平台接入风险

| 平台 | 风险 | 应对 |
|---|---|---|
| 抖店 | 反爬、UI 改版（路径 A 已积累经验） | 复用路径 A 的方法论 |
| 天猫 | ISV 资质要求、千牛后台复杂 | 全 Playwright，不依赖官方 API |
| 京东 | 商智后台访问限制 | 同上 |

### 10.2 数据迁移风险

- mvp_* → omni_* 字段 1:N 拆分（mvp_sku → sku + sku_platform_link）
- 应对：完整迁移 SQL + 干跑模式 + 备份 + 回滚脚本

### 10.3 用户体验风险

- Sidebar 大改（5 段 17 项 → 7 项）可能让老板暂时找不到东西
- 应对：旧路由全部重定向 + 内置"找东西"搜索 + 7 天宽限期保留路径 A 的 sidebar 入口

### 10.4 工程风险

- 4-6 周工期紧
- 应对：阶段性交付，每周可独立上线（不必等到 Week 6）
