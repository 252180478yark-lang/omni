### 2.2 V-B-02：数据迁移完整性

```sql
-- 验证 1：mvp_sku 完全迁移
SELECT
  (SELECT COUNT(*) FROM archived_mvp_sku) AS old_count,
  (SELECT COUNT(*) FROM omni_core.sku) AS new_count;
-- 预期：相等

-- 验证 2：每条 mvp_daily_metric 都有对应 omni_data.daily_metric
SELECT COUNT(*) FROM archived_mvp_daily_metric m
LEFT JOIN omni_data.daily_metric n ON
  n.date = m.date AND n.metric_name = m.metric_name
  AND EXISTS (
    SELECT 1 FROM omni_core.sku_platform_link spl
    WHERE spl.id = n.platform_link_id AND spl.spu_id = m.sku_id
  )
WHERE n.id IS NULL;
-- 预期：0

-- 验证 3：所有决策日志保留状态
SELECT COUNT(*) FROM archived_mvp_decision_log a
LEFT JOIN omni_decision.decision_log b ON
  b.title = a.title AND b.created_at = a.created_at
WHERE b.id IS NULL;
-- 预期：0
```

### 2.3 V-B-03：跨平台聚合查询

```sql
-- 验证：跨平台聚合（一个 SPU 抖店+天猫 GMV）

  spl.platform,
```

## 五、业务流层验收（4 条使用流）

### 5.1 流 1：早晨 5 分钟巡店

```
T+0    08:30 三平台 runbook 启动
T+9 分 三平台抓取 + 异动检测 + 跨平台聚合完成
T+10   企微推送
T+30   你打开 /workspace
T+30~35 处理 3-5 张卡片 → 切到 SKU 详情 → 启动诊断 / 采纳建议
```

**通过条件**：5 分钟内完成处理；任何卡片可一键跳到 SKU 详情。

### 5.2 流 2：单 SKU 深聊诊断

```
你：进 SKU 详情 → 切到「AI 诊断」Tab → 点「启动深度诊断」
系统：圆桌讨论（4 视角）+ 拉知识库 + 跨平台数据
T+90s 圆桌结束 → 自动落 decision_log
你：阅读 → 「采纳」→ 自动建 change_event（待执行，关联多平台 instance）
```

**通过条件**：90 秒内完成；决策自动落库；采纳后 change_event 正确预填。

### 5.3 流 3：动作执行登记

**两条路径**：

#### 3a：从决策采纳

```
点「采纳」→ 自动建 change_event 草稿（预填 SKU/平台/asset_type/intent）
你：执行后回来确认 + 上传截图
```

**通过条件**：草稿字段全部预填正确；确认后状态变 executed。

#### 3b：手动登记

同路径 A，加多平台支持（可选 1 个或多个平台同步登记）。

### 5.4 流 4：周度复盘

```
周日 21:00 进 /insights/weekly
看到：
  - 本周决策状态（已执行/已验证/待执行）
  - AI 命中率（含本周 vs 上周对比）
  - 跨平台 ROI 对比
  - ≥6 张图表
  - 顶部成功案例 / 失败教训
你：处理 pending 决策 + 归档成功案例 + 写失败教训
T+30 分钟 完成
```

**通过条件**：30 分钟内完成；所有图表渲染 ≤ 3 秒。

## 六、飞轮层验收

### 6.1 V-B-50：AI 命中率

**测试期**：路径 B 上线后第 1-4 周。

```sql
-- 每周计算一次
SELECT
  DATE_TRUNC('week', verified_at) AS week,
  COUNT(*) AS total,
  COUNT(*) FILTER (WHERE verification_result->>'verdict' = 'positive') AS positive,
  ROUND(
    COUNT(*) FILTER (WHERE verification_result->>'verdict' = 'positive')::numeric /
    COUNT(*) * 100, 2
  ) AS hit_rate_pct
FROM omni_decision.decision_log
WHERE status = 'verified'
  AND verified_at >= NOW() - INTERVAL '4 weeks'
GROUP BY week ORDER BY week;
```

**通过条件**：连续 4 周 hit_rate_pct ≥ 60%。

## 八、稳定性验收

### 8.1 三平台 7 天稳定性

```sql
SELECT
  platform,
  COUNT(*) AS total,
  ROUND(COUNT(*) FILTER (WHERE status = 'success')::numeric / COUNT(*) * 100, 2) AS rate
FROM omni_data.scout_run
WHERE started_at >= NOW() - INTERVAL '7 days'
GROUP BY platform;
```

**通过条件**：每个平台 rate ≥ 95%。

### 8.2 数据完整性日检

每天 03:00 跑：

```sql
-- 验证：每个活跃 SKU × 每个平台 × 每天都有数据
WITH expected AS (
  SELECT spl.id AS link_id, d::date AS date
  FROM omni_core.sku_platform_link spl
  CROSS JOIN generate_series(CURRENT_DATE - 7, CURRENT_DATE - 1, '1 day') d
  WHERE spl.status = 'active'
)
SELECT e.link_id, e.date AS missing
FROM expected e
LEFT JOIN omni_data.daily_metric m ON
  m.platform_link_id = e.link_id AND m.date = e.date AND m.metric_name = 'gmv'
WHERE m.id IS NULL;
```

**通过条件**：返回 0 行（即无缺失）。允许偶发漏抓 ≤ 1%。

## 十一、回滚方案

如路径 B 重大问题，需要回滚到路径 A：

```sql
-- 1. 重命名 archived_mvp_* 表回 mvp_*
ALTER TABLE archived_mvp_sku RENAME TO mvp_sku;
ALTER TABLE archived_mvp_daily_metric RENAME TO mvp_daily_metric;
-- ... 其他表
-- 2. 在前端改 .env 切换 USE_OMNI_SCHEMA=false
-- 3. omni_* schema 保留（数据不丢）
```

回滚后路径 A 完全可用，新增到 omni_* 的数据需要重新决定如何合并。
