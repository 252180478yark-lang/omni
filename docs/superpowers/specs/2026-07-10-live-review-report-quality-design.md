# 直播复盘报告质量升级设计

日期：2026-07-10

## 背景

直播复盘功能已经有后端链路：`generate_live_review` 调 `scout-agent` 抓罗盘直播事实卡，再把事实卡和逐字稿交给 Gemini 生成报告。现有实现可以跑通，但输出更像“分析说明书”，还不够像老板复盘会里能直接用的操盘口径。

本轮选择方案 2：不重做采集，也不先做 UI，而是升级 prompt 和报告模板，让结果更聚焦“这场最大短板是什么、下一场主播和中控应该怎么改”。

## 目标

第一版升级要做到：

1. 报告开头先给老板能直接判断的结论，而不是先铺数据。
2. 逐段诊断必须绑定事实卡里的关键讲解段，避免泛泛点评。
3. 每条建议都落成“主播怎么说 / 中控怎么做 / 什么时候做”。
4. 数字仍只来自事实卡，因果仍按“观察 / 假设 / 需验证”分层。
5. 没有逐字稿时可以降级成数据骨架复盘，但必须明说话术诊断不可完成。

## 非目标

本轮不做：

1. 不改罗盘接口采集逻辑。
2. 不改 `live_factcard.py` 的波峰波谷算法。
3. 不做专门前端页面。
4. 不引入录音、ASR、自动转写链路。
5. 不做多场直播对比。

这些都可以作为第二轮升级。

## 现有入口

主要文件：

- `services/knowledge-engine/app/mcp/tools/live_review.py`
- `services/knowledge-engine/app/services/live_review_service.py`
- `services/knowledge-engine/config/prompts/live_review.system.md`
- `services/knowledge-engine/config/prompts/live_review.user.md`
- `services/scout-agent/app/services/live_collect.py`
- `services/scout-agent/app/services/live_factcard.py`

运行入口：

```text
generate_live_review(
  room_id="<罗盘直播大屏 live_room_id>",
  transcript="<逐字稿文本>",
  transcript_has_timestamps=true|false,
  focus="<本次关注点，可空>",
  polish=true
)
```

## 报告结构

升级后的报告固定输出以下章节。

### 0. 一句话结论

用一段话判断这场主要短板属于哪一类：

- 流量不足：没人来或流量结构太弱。
- 承接不足：有人来，但点击/成交没接住。
- 话术错位：该留人时在念参数，该逼单时没有逼单。
- 中控缺位：波峰/掉人/出单窗口没有配合弹卡、福袋、改价、追单。
- 数据不足：事实卡或逐字稿不够，不能下判断。

### 1. 老板先看三个问题

用事实卡回答：

1. 人有没有来？
2. 来了有没有点？
3. 点了有没有买？

每个问题必须包含“观察”和“判断”。判断如果带归因，必须标“假设”。

### 2. 全场最大问题

输出三块：

- 观察：只引用事实卡数字。
- 判断：指出最短板的一环。
- 需验证：列出需要录屏、评论、投流数据或人工确认的点。

### 3. 关键讲解段复盘

只分析事实卡里“选中的关键讲解段”，不展开全部讲解段。

每段固定结构：

```text
#### [时间窗] [段标签]

- 当时数据状态：
- 主播实际：
- 剧本本该：
- 中控配合：
- 后 3 分钟结果：
- 缺口：
- 下一场原话：
- 中控动作：
```

“下一场原话”必须是一句或几句可直接拿给主播说的话，不能只写原则。

### 4. 主播线

按话术类型总结：

- 念参数是否过多。
- 痛点有没有讲成生活场景。
- 有没有明确引导点击。
- 在线峰值时有没有逼单。
- 掉人时有没有留人动作。

### 5. 中控线

按关键窗口总结：

- 进入涌入时有没有弹商品卡或承接动作。
- 在线峰值时有没有收割动作。
- 掉人时有没有福袋、互动或换节奏。
- 出单后有没有追单和关联推荐。
- 看不到的动作必须写“需录屏确认”。

### 6. 下一场直播 SOP

给一张行动表：

| 场景 | 主播说什么 | 中控做什么 | 看哪个数据 |
|---|---|---|---|
| 开场 3 分钟 |  |  |  |
| 新流量涌入 |  |  |  |
| 在线上升 |  |  |  |
| 在线峰值 |  |  |  |
| 掉人 |  |  |  |
| 点击高但不买 |  |  |  |
| 出单后 |  |  |  |
| 收尾 |  |  |  |

### 7. 黄金话术模板

只有事实卡显示“进入、点击、成交链路较顺”的段，才可以沉淀模板。没有黄金段时，必须写“本场没有足够证据沉淀黄金模板”，不能硬编。

## Prompt 调整

### System Prompt

需要强化：

1. 角色从“复盘官”升级成“老板复盘会里的操盘手”。
2. 第一任务是判定短板环节，不是复述数据。
3. 建议必须落地到主播话术和中控动作。
4. 禁止把“点击为 0”直接判成话术差，必须结合在线人数。
5. 中控动作看不到就标“需录屏确认”。

### User Prompt

需要重构输出模板：

1. 把“关键讲解段逐段分析”前移到结论之后。
2. 增加“老板先看三个问题”。
3. 增加“下一场直播 SOP”表格。
4. 增加“下一场原话”字段。
5. 明确没有逐字稿时的降级输出。

## 验收标准

用一次真实或历史 room_id 跑 `generate_live_review`，报告必须满足：

1. 开头 300 字内能看出最大问题。
2. 每个关键讲解段都有“下一场原话”和“中控动作”。
3. 没有新增事实卡之外的数字。
4. 中控不可见动作没有被写死为事实。
5. Top 建议没有“提升转化、优化话术”这类空话。
6. 没有使用禁用 AI 腔词汇。
7. `trace.final_prompt` 包含新版章节结构。

## 验证方式

第一轮验证：

1. 跑 `docker exec omni-knowledge-engine bash -c "cd /app && PYTHONPATH=/app python -m app.mcp.doctor"` 确认工具注册正常。
2. 通过 `POST /api/v1/mcp/catalog/exec` 调 `generate_live_review`，先用 `polish=false` 验证事实卡，再用 `polish=true` 验证完整报告。
3. 人工检查 markdown 是否满足验收标准。

第二轮可补自动测试：

1. 对 prompt 文件做快照测试，确认章节标题存在。
2. 对输出做禁词扫描。
3. 对输出做“新增数字”风险扫描。

## 风险

1. 如果事实卡本身选段不准，prompt 再强也会围绕错误段分析。这个留给第二轮事实卡升级。
2. 如果逐字稿不带时间戳，对齐只能近似，报告必须提醒。
3. 如果 Gemini 输出过长，关键建议可能被淹没，所以模板必须把结论和 SOP 前置。
4. 如果没有真实 room_id，本轮只能做 prompt 级验证，不能证明业务效果。

## 后续升级

下一轮可以考虑：

1. 给 `live_factcard.py` 增加确定性段评分。
2. 增加“启动体检”：容器、罗盘登录态、room_id、AI provider 一键检查。
3. 做专门前端页面，支持粘贴 room_id 和上传逐字稿。
4. 把黄金段沉淀到 prompt_rules 或话术模板库。
